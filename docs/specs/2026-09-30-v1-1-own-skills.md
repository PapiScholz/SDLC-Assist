# Spec: v1.1 — own phase skills (`sdlc-debugging`, `sdlc-qa-gate`, `sdlc-release`)

Phase: deployment
Status: closed

Owner: Ezequiel Scholz
Repo: `PapiScholz/SDLC-Assist` (in production, v0.1.1)
Parent: `docs/specs/2026-09-29-sdlc-skill-design.md` (v1, closed)

## Objective

Ship the three phase skills that v1 deferred, so that a user who installs
`SDLC-Assist` and nothing else never reaches the missing-skill question on
the bug path, the Testing phase or the Deployment phase.

- `sdlc-debugging`: the bug route inside Requirements analysis. Localise
  the fault before writing the short spec, so the spec states a cause, not
  a symptom.
- `sdlc-qa-gate`: the Testing phase. Run every applicable verification
  layer against the built artifact and report what was verified, what was
  not, and the residual risk. Never say "green".
- `sdlc-release`: the Deployment phase. Decide the version from the
  commits, update version files and changelog, validate, tag and publish,
  following the project's existing release mechanism when there is one, and
  only when the user asked in the current turn.

Users: the same as v1. Docs in English; the skills reply in the user's
language.

Success looks like: on a fresh machine with only this repo installed,
`which.js` reports an installed skill for every phase, and each of the
three skills produces its artifact on the reference scenarios below.

## Design decisions

- **Own rewrites, generic, in English.** The skills take their structure
  and lessons from the owner's private `qa-push` command, the
  `release-engineer` skill and the debugging discipline the owner already
  uses, but none of their text and none of their project specifics (no
  Electron, Next.js or POS references). Ecosystems covered by detection:
  npm/pnpm/yarn, Python, Rust, Go, JVM (Gradle/Maven); anything else falls
  back to "no runner detected, verify by hand".
- **Own skills are the default; alternatives stay listed.** Phase sheets
  recommend `sdlc-*`; `alternatives` keep `superpowers:systematic-debugging`,
  `debugging-strategies`, `qa-push`, `release-engineer`. `which.js` shows
  both and the user chooses. Names never clash with the alternatives.
- **Markdown skills, no new scripts.** Each skill is a `SKILL.md` plus
  optional `references/`. Detection of the stack reuses what `where.js`
  already emits (`signals.testRunner`, `releaseWorkflow`, `git`); the
  skills instruct the agent to run `where.js` when they need those facts
  rather than re-implementing detection.
- **Same safety regime as `sdlc`.** No state-changing git without the
  user's explicit request in the current turn; nothing installed; the test
  suite runs only when the user asked or when the gate itself is the
  request.

## The three skills

### `sdlc-debugging` (Analysis, bug route)

Enters when `where.js` classifies the request as `bug` or `complaint` and
the user confirms Analysis. Produces the cause section of the short spec.

Protocol, four steps, each with an exit criterion:

1. **Reproduce.** Get a failing observation the agent can re-run: a test,
   a command, a request. If none is possible, record exactly why and what
   evidence stands in for it. Exit: one command or step that shows the
   fault.
2. **Localise.** Narrow to the smallest unit that still fails: file,
   function, input. Use logs, bisection over inputs or commits
   (`git bisect` is read-only on the working tree state the user chose),
   and the request card's "where it happens". Exit: a file and a line
   range, or an explicit "not localisable with current evidence".
3. **Explain.** State the cause as a sentence that predicts the symptom.
   Rule from the owner's practice: if the last action before the symptom
   was the agent's own, that action is the first suspect; two sources that
   disagree mean one of them is lying, find which before going deeper.
   Exit: a cause and one disproof attempt that failed to disprove it.
4. **Hand off.** Write the "Cause" and "Evidence" lines of the request
   card and the short spec (`references/request-card.md` gains those two
   lines as optional sixth and seventh). The fix is Development's job.

Never: change product code during these steps (a diagnostic print or a
failing test is allowed and is removed or kept deliberately), or declare a
cause without a reproduction or an explicit statement that none exists.

### `sdlc-qa-gate` (Testing)

Enters when the plan's tasks are closed and the user asks for the gate, or
when `where.js` infers `testing` and the user confirms. Produces a report
table, never a verdict word.

Layers, cheapest first; every applicable layer runs or is listed as "not
run" with the reason:

| Layer | Applies when | What passes |
|---|---|---|
| static | a type checker or linter is configured | typecheck and lint exit 0 |
| unit | `signals.testRunner.kind` is set | full suite, zero unjustified skips |
| build | the project has a build step | the artifact exists and its manifests are complete |
| runtime | the diff touches UI, API, config or dependencies | the built artifact starts in production mode and answers on its port within a timeout |
| functional | the diff touches UI or API | changed routes or endpoints answer without errors against the runtime layer; an authenticated health call returns 200 before any authenticated check |
| regression | shared modules changed (utils, stores, schemas) | suites of untouched modules that import them still pass |

Before running layers, the gate maps the diff: for each changed file, its
domain (logic, API, UI, integration, config, CI, docs), existing coverage,
and nature (`dead-code`, `refactor`, `new-logic`, `ci-infra`, `config`).
`new-logic` without a covering test is a gap the report names; the gate
proposes the test but writes it only if the user asks.

Report format, mandatory:

```
| Layer | Verified | Not verified | Residual risk |
```

plus one line per gap. The words "green", "100%" and "safe" never appear
as a verdict. The report ends with the next step: `sdlc close` for
Testing when the residual risk is accepted, or the fix list otherwise.

Never: run dev mode as a substitute for the built artifact; kill processes
by broad pattern; claim a layer passed that did not run.

### `sdlc-release` (Deployment)

Enters when Testing is closed and the user asks for a release in the
current turn. Produces a version decision, updated version files and
changelog, a tag and a published release, in that order, stopping at the
first failure.

Steps:

1. **Detect** the release mechanism already in the repo: a release
   workflow (`.github/workflows/*release*`), a release script, `changesets`,
   `semantic-release`, `release-please`. If one exists, the skill drives
   that mechanism (or explains how to trigger it) instead of reimplementing
   it. Only without one does it perform steps 2 to 6 itself.
2. **Classify** the commits since the last tag: breaking → major,
   feature → minor, fix/docs/ci → patch; when mixed, the safer lower bump;
   reasoning stated before acting. Honour a higher version already pinned
   in the version file.
3. **Update** every version source the project has (`package.json`,
   `pyproject.toml`, `Cargo.toml`, plugin manifests, a `version:`
   frontmatter) and the changelog: consume `## [Unreleased]` when present,
   otherwise prepend an entry grouped Added / Changed / Fixed / CI.
4. **Validate** with the project's own checks (tests, build or pack dry
   run, version consistency across sources). Any failure stops the release.
5. **Commit, tag, push, publish** using the forge's tooling (`gh release
   create` or equivalent), with the changelog entry as notes.
6. **Publish guidance** for the ecosystem's registry (npm, PyPI, crates,
   Go modules) without executing the publish unless the user asked for it
   too.

Every command in steps 5 and 6 requires the user's explicit request in the
current turn; the skill lists the exact commands it is about to run and
runs them only after the user says so. In an environment where a guard
blocks these commands, the skill reports the block and stops.

Never: force-push, rewrite tags, publish to a registry unasked, or continue
after a failed validation.

## Testing strategy

Markdown skills have no unit tests; the gates are:

- `check-frontmatter.js`: nine skills, `name` equals folder, `description`
  present, `version` present on the own skills.
- `check-skill-sections.js`: section parity with the contracts above; red
  run by renaming one heading.
- `check-sheets.js`: `analysis.md` recommends resolve.
- CI `install-smoke`: after `npx skills add`, the three directories exist
  and `which.js --phase testing` run against the temp home reports
  `sdlc-qa-gate` as installed.
- Dogfood on this repo, recorded in `docs/ci-red-runs.md`: (a) run
  `sdlc-qa-gate` on the v1.1 diff and paste the report table; (b) run
  `sdlc-release` in detect mode: it must find `.github/workflows/release.yml`
  and recommend pushing to `main` instead of tagging by hand; (c) run
  `sdlc-debugging` on a seeded fault in a scratch repo (a failing self-test
  after a one-line edit) and paste the Cause/Evidence lines.

Reference scenarios (fresh temp home, only this repo installed):

| # | Phase | Expect |
|---|---|---|
| 1 | analysis, request `bug` | `which.js --phase analysis` lists `sdlc-debugging` installed; no second question |
| 2 | testing | `sdlc-qa-gate` installed; report table produced on a scratch npm project with one changed file |
| 3 | deployment | `sdlc-release` installed; on a repo with a release workflow it drives that workflow; on a repo without one it stops before step 5 until the user asks |

## Boundaries

- Always: reply in the user's language; state what was not run and why;
  reuse the project's own tooling before inventing commands.
- Ask first (own question inside the skill): writing a missing test in
  the gate; every command of release steps 5 and 6.
- Never: state-changing git without the user's request in the current
  turn; product code changes inside `sdlc-debugging`; "green"/"safe"
  verdicts in the gate; force-push, tag rewrite or unasked registry
  publish in the release.

## Success criteria

- Nine `SKILL.md` pass frontmatter and section gates; CI green on Ubuntu
  and Windows including the extended `install-smoke`.
- The three reference scenarios pass on a fresh temp home.
- The three dogfood runs are recorded.
- `README` and `missing-skill.md` name the three skills with their install
  command.
